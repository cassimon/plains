# Plan: Import edited Process / Experiment PDFs (+ measurement data)

**Status:** Core parse/diff/validate/apply engine **implemented** in
`frontend/src/lib/pdfImport.ts` (covered by `frontend/tests/pdf-roundtrip.spec.ts`). Still to do:
the modify-vs-new UI, the ownership/plane-sharing server enforcement (§7), and measurement-data
auto-attach (§8).

This document specifies how the app ingests a PDF that was produced by the export flow (optionally
with the user's edits and/or attached measurement data) and reconciles it with the app's data.

## Implementation notes (as built)

- The canonical payload travels in a **hidden read-only AcroForm field** `plains:payload` (not the
  file attachment) because pdf-lib round-trips form-field values reliably; the payload also carries a
  **`fields` snapshot** of every editable field's exported value, so edit-detection is a direct
  `current !== snapshot` compare rather than re-deriving export formatting. See
  `pdfSchema.ts` (`embedPayload`/`readPayload`/`migratePayload`) and `pdfImport.ts`
  (`importPdf` → `{ original, edited, edits, errors }`, plus `validateEdit`, `applyFieldValue`).
- Only **stored** quantities are editable form fields; derived display values (per-solvent volume,
  molar concentration) are static text, so every editable field maps 1:1 back onto the entity.

---

## 1. Goal & guarantees

The exported PDF carries two things (export plan §4):
1. a **canonical JSON payload** (`plains.json` attachment) = the exact `Process` / `Experiment` at
   export time, tagged with `schemaVersion` and the app ids;
2. **AcroForm form fields** = the human-editable overlay for "important quantities", with field names
   that decode back to data paths.

Import must:
- attach uploaded **measurement data to the correct Process/Experiment automatically** using the
  embedded ids;
- detect whether the user **edited** any field vs the canonical payload;
- let the user choose **modify existing** vs **create new** when edits exist;
- **validate** edited values and surface errors without corrupting data;
- enforce **ownership / plane-sharing** copy rules.

---

## 2. Reading the PDF (frontend, pdf-lib)

New `frontend/src/lib/pdfImport.ts`:

1. `PDFDocument.load(bytes)`.
2. Locate the `plains.json` attachment → parse → `Serialized{Process|Experiment}`.
   - Fallback: read ids/version from document metadata if the attachment was stripped; if neither
     exists, reject with "This PDF was not generated by Plains."
3. `const form = pdfDoc.getForm()`; read every field value; `decodeFieldName(name) → path`.
4. Also detect **attached measurement files** (any non-`plains.json` attachments) and/or accept a
   separate measurement upload alongside the PDF (matches the existing upload flow —
   `lib/uploadFlow.ts`, `useStartOrAddUpload.tsx`).

---

## 3. Schema-version migration (downward compatibility)

- Compare `payload.schemaVersion` to `PDF_SCHEMA_VERSION`.
- Maintain an ordered **migration ladder** `migrations[from → from+1]` in `pdfSchema.ts` (co-located
  with the version constant so a bump forces the author to add a migration). Apply migrations
  sequentially until the payload matches the current shape.
- If `payload.schemaVersion > PDF_SCHEMA_VERSION` (PDF newer than app) → refuse with a clear message
  ("This PDF was made by a newer version of Plains; please update.").
- The field-name codec is versioned implicitly by the same ladder — old codecs decode old PDFs.

---

## 4. Edit detection (form overlay vs canonical payload)

For each form field: rebuild the **expected** value by reading the same `path` out of the canonical
payload (via the shared codec) and formatting it exactly as export did. Compare to the field's current
value.

- Build `edits: { path, oldValue, newValue }[]`.
- **Normalize before comparing** (trim, number formatting, unit casing) so a no-op re-save of an
  untouched field is not flagged. This mirrors export formatting precisely — keep format helpers
  shared between export and import.
- If `edits.length === 0` → straight import/attach, no prompts (§6, §7 still apply for ownership).

---

## 5. Validation & error handling

Each edited field is validated against the target type (numbers for `annealingTemp`, dates for
`date`/`endDate`, enum membership for dropdowns, etc.):

- On a **valid** edit → stage it for apply.
- On an **invalid** edit → collect into `errors: { path, value, reason }[]` and show them to the user
  as a list of messages. Per the requirement, the offending field is then:
  - **left blank** when the result is a **new** Process/Experiment, or
  - **not modified** (keep the app's current value) when **modifying** an existing one.
- Import proceeds for the valid fields; the error report is non-blocking but clearly surfaced.

---

## 6. Modify vs. create-new decision

When `edits.length > 0`, prompt the user (Mantine modal):

- **Propagate edits (modify)** → update the existing Process/Experiment (by `payload.process.id` /
  `experiment.id`) with the valid edited fields; invalid fields keep their current app value (§5).
- **Create new** → clone the payload into a brand-new entity (fresh `id`), apply valid edits, invalid
  fields left blank (§5). Link it appropriately (new Process, or new Experiment pointing at the same
  `processId`).

If the referenced entity **no longer exists** in the app, offer only "Create new".

---

## 7. Ownership & plane-sharing copy rule

Determine the uploader (`current_user`) vs the entity `owner_id` (backend `Process.owner_id`,
`Experiment.owner_id` — see `backend/app/models.py`).

- If the entity **belongs to a different user**:
  - **Default:** automatically make a **copy** owned by the uploader, and **inform the user**
    ("This process belongs to <owner>; a copy was created under your account.").
  - **Exception:** if the entity's **plane is shared** with the uploader (a `PlaneShare` row links the
    plane to `current_user` — see `backend/app/api/routes/planes.py`), allow **in-place modify**
    instead of forcing a copy (subject to the modify/new choice in §6).
- Resolve the entity→plane link via its `CanvasElement` (`kind`,`entity_id`) membership, then check
  `PlaneShare`. This ownership/sharing check is authoritative and must be enforced **server-side**,
  not just in the UI.

---

## 8. Measurement-data auto-attach

- The embedded `process.id` / `experiment.id` route uploaded measurement files to the right entity
  without the user re-selecting a target — feeding the existing upload/result creation path
  (`ExperimentResults`, `results` route). If the target was copied/newly-created per §6/§7, attach to
  the resulting entity's id.
- Reuse the recognized-file-group logic already in the upload flow so measurement files map to the
  correct substrate/device groups.

---

## 9. Backend vs frontend split

- **Frontend:** parse PDF, migrate, diff, validate, drive the modify/new + error UI.
- **Backend:** a new endpoint (e.g. `POST /processes/import` / `/experiments/import`) that enforces
  ownership/sharing (§7), performs the create-copy-vs-modify write transactionally, and returns the
  resulting entity. Do **not** trust the client for the ownership decision. Add `IntegrityError`-safe
  handling per the CORS-masking gotcha in `CLAUDE.md`.

---

## 10. Open questions
1. Should measurement files be embedded **inside** the PDF, uploaded **alongside** it, or both?
2. For "modify existing", do we snapshot/version the pre-import state for undo?
3. Conflict handling if the app entity changed since the PDF was exported (payload is stale) — warn,
   or three-way merge?
4. Bulk import (a folder of edited PDFs) — out of scope for v1?
